## Context and Problem Statement

All nine integration requirements in `ARC-001-REQ-v1.0` (INT-001 to INT-009) specify **event-driven** integration using a **publish/subscribe** pattern. The canonical data model those integrations map to is defined in `ARC-001-DATA-v1.0` §Context 1 — PERSON, UNIT, TEACHING_PERIOD, UNIT_OFFERING, ENROLMENT and INSTITUTIONAL_ROLE_ASSIGNMENT.

**What is not decided is what provides the publish/subscribe.** The requirements state a pattern; they do not state an architecture. Nine integrations can each implement event-driven messaging independently, or they can share mediating infrastructure, and those are materially different systems with different costs, failure modes and operating models.

This decision governs WP5 and is a precondition for WP8's target state. It also has a consumer outside this engagement: project 002's INT-001 provisioning build depends on how identity and enrolment events reach a capture platform.

### Why the decision is needed now

The current estate has no mediation at all. Seven integrations run as point solutions — a nightly flat-file, LTI plus manual CSV, semi-manual scripts with a single-person dependency, manual re-keying of placement grades, and manual hierarchy updates [SL-C1]. Risk R-006 (integration estate fragility) and BR-004 (integration fragility and manual handling eliminated) both trace directly to the absence of any mediating layer.

Deciding integration-by-integration, as has happened historically, is what produced the current estate. That is the pattern this ADR exists to break.

### Regulatory and policy context

- **Privacy Act 1988** — flat files on shared storage and CSV cohort extracts create unnecessary copies of personal information (DR-003, NFR-C-001)
- **ASD Essential Eight** — service-to-service credentials and shared accounts in point solutions work against the ML2 target (NFR-SEC-002)
- **RIFF governance** — solutions duplicating licensed capability must justify why the incumbent is unsuitable [SGP-C1]; this applies to any middleware purchase

## Considered Options

1. **Option A** — Point-to-point event-driven integration
2. **Option B** — Central integration broker (iPaaS or self-hosted)
3. **Option C** — LMS as integration hub
4. **Option D** — Do Nothing (baseline)

### Option A: Point-to-point event-driven integration

**Description**: Each integration is built directly between source and target using each platform's native APIs and webhooks. No shared mediating infrastructure. The canonical model is enforced by convention and code review rather than by a runtime component.

**Implementation approach**: Nine integrations built independently to a common interface standard, each publishing and consuming change events against the canonical entity definitions. A published integration standard document governs conformance.

**Wardley evolution stage**: Custom-built (0.35) — the integrations are bespoke assemblies of product APIs.

**Good**:

- ✅ No new licence cost — satisfies BR-002 and Principle 19 without argument
- ✅ No new shared runtime dependency, so no new single point of failure against NFR-A-001
- ✅ Fastest path for any *single* integration; INT-001 could start immediately
- ✅ No vendor lock-in at the mediation layer
- ✅ Each integration can use the most appropriate native mechanism

**Bad**:

- ❌ Conformance to the canonical model is unenforceable at runtime — it relies on discipline, and the current estate is evidence of how that ends
- ❌ Observability is per-integration; NFR-M-001 requires assembling nine separate views
- ❌ n×(n−1) coupling growth — each new platform multiplies integration work
- ❌ Credential sprawl: nine sets of service-to-service credentials to manage against NFR-SEC-002
- ❌ Retry, replay and dead-letter handling reimplemented nine times, or omitted eight times
- ❌ **This is architecturally what the university already has**, differing mainly in being event-driven rather than batch

**Cost analysis** *(indicative — no costing baseline exists for 001; see Assumptions)*:

| | Estimate |
|---|---|
| CAPEX | Nil licence. Integration build effort ×9, each carrying its own error handling |
| OPEX | Nil licence. Support effort distributed and duplicated |
| 3-year TCO | Lowest visible cost, highest hidden cost. Cost appears in support load and in the next rationalisation |

---

### Option B: Central integration broker

**Description**: A single mediating layer — managed iPaaS or self-hosted event broker — through which integrations publish and subscribe. The broker holds the canonical schema, enforces contracts, and provides retry, replay, dead-letter and observability as shared services.

**Implementation approach**: Broker deployed in an Australian region. Each platform publishes change events to topics defined by the canonical model. Subscribers consume without knowing the source. Schema registry enforces DR-001 conformance at runtime.

**Wardley evolution stage**: Product (0.65) — mature market, multiple vendors, well-understood operating model.

**Good**:

- ✅ **Canonical model enforced at runtime**, not by convention — the strongest available treatment for Principle 6 and DR-001
- ✅ Single observability plane satisfies NFR-M-001 directly
- ✅ Retry, replay and dead-letter implemented once (NFR-M-002)
- ✅ New platforms integrate once to the broker rather than n times — the estate scales without multiplying coupling
- ✅ Centralised credential and audit position supports NFR-SEC-002 and NFR-C-003
- ✅ Replayable event history materially improves recovery from the failure modes in R-006

**Bad**:

- ❌ **New licence or hosting cost against BR-002** — must be justified under Principle 19 and the RIFF duplication rule
- ❌ **Creates a shared runtime dependency**: broker unavailability affects every integration simultaneously, a new risk against NFR-A-001
- ❌ Requires operational capability the AV/integration team does not currently hold — skills and on-call
- ❌ Slowest start; INT-001 waits for platform selection and standing up
- ❌ Vendor lock-in risk at the mediation layer, mitigated only by open protocols
- ❌ Risk of becoming a second source of truth if state accumulates in the broker, contrary to Principle 5

**Cost analysis** *(indicative)*:

| | Estimate |
|---|---|
| CAPEX | Broker selection, deployment, schema definition, first two integrations |
| OPEX | Licence or hosting, ongoing operation, skills uplift |
| 3-year TCO | Highest visible cost, lowest marginal cost per additional integration |

---

### Option C: LMS as integration hub

**Description**: Blackboard Ultra acts as the integration point. Other platforms integrate to the LMS, which holds enrolment and role state and propagates onward via LTI and its own APIs.

**Implementation approach**: SIS feeds the LMS; capture, portfolio, assessment and collaboration platforms integrate to the LMS via LTI 1.3 names-and-roles rather than to the SIS directly.

**Wardley evolution stage**: Product (0.60) — using an existing licensed product's integration surface.

**Good**:

- ✅ No new licence cost; strongest Principle 19 position of the three active options
- ✅ LTI 1.3 names-and-roles is a genuine standard, already required by several integrations
- ✅ The LMS already holds much of the required state
- ✅ Fewest new components to operate

**Bad**:

- ❌ **Makes the LMS a source of truth for enrolment and role, directly contrary to Principle 5** — the SIS is authoritative, and this option interposes a cache between it and everything else
- ❌ Couples the entire estate to one vendor's integration surface — the most severe lock-in of any option, and it degrades NFR-I-002
- ❌ LTI does not cover all nine integrations; placement grades (INT-005) and analytics export (INT-009) fall outside it
- ❌ LMS availability becomes a dependency for integrations that have nothing to do with teaching delivery
- ❌ Constrains the WP8 future state: replacing the LMS later would mean rebuilding every integration

**Cost analysis** *(indicative)*:

| | Estimate |
|---|---|
| CAPEX | Configuration effort; lowest of the three active options |
| OPEX | Nil incremental licence |
| 3-year TCO | Lowest cash cost, highest strategic cost. Exit cost from the LMS rises sharply |

---

### Option D: Do Nothing (baseline)

**Description**: Retain the current arrangement — nightly flat-file, LTI plus manual CSV, semi-manual scripts, manual re-keying, manual hierarchy updates.

**Good**:

- ✅ No cost, no change, no new risk introduced
- ✅ Staff know the current failure modes

**Bad**:

- ❌ Fails BR-004 outright — this requirement exists to end exactly this arrangement
- ❌ Fails NFR-P-001; the nightly batch cannot propagate within minutes
- ❌ Fails NFR-SEC-003 and Principle 12; manual CSV provisioning persists
- ❌ Leaves R-006, R-008 and R-018 unmitigated, including sensitive placement information re-keyed by hand
- ❌ Flat files on shared storage and CSV extracts remain a standing privacy exposure (DR-003)
- ❌ Course cloning single-person dependency persists

**Retained as a genuine baseline**, not a strawman: the RIFF pause provision permits closing a request. But the evidence against it is unusually strong — four requirements and three risks all fail.

## Decision Outcome

**Chosen option: Option B — Central integration broker**, with a phased adoption path that begins with the two integrations carrying the highest failure cost.

### Y-Statement

> In the context of **replacing nine point-to-point and manual integrations across the L&T ecosystem**,
> facing **a canonical model that cannot be enforced at runtime and an estate whose fragility is the engagement's primary finding**,
> we decided for **a central integration broker holding the canonical schema**,
> and against **point-to-point event-driven integration and LMS-as-hub**,
> to achieve **runtime conformance to the canonical model, single-plane observability, and integration cost that does not multiply with each new platform**,
> accepting **a new licence or hosting cost, a new shared runtime dependency, and an operational skills uplift the team does not currently hold**.

### Justification

**Why not Option A**, despite its cost advantage: point-to-point makes canonical conformance a matter of discipline. The current estate is the evidence of where that leads — nine integrations built independently, each reasonable at the time. Option A is architecturally the status quo made faster. It would satisfy NFR-P-001 while leaving Principle 6 unenforceable and NFR-M-001 unmet.

**Why not Option C**, despite the strongest Principle 19 position: it violates Principle 5, which is rated CRITICAL. Making the LMS authoritative for enrolment and role interposes a cache between the SIS and every consumer, and couples the whole estate to one vendor's integration surface. It also constrains WP8 — a future LMS decision would require rebuilding everything. The cash saving is real; the strategic cost is larger and less visible.

**Why Option B despite the cost**: it is the only option that enforces the canonical model at runtime rather than by convention, and enforcement is the difference between a model that governs and a model that documents. Principle 19 requires existing licensed capability to be evaluated first — that evaluation is a condition of this decision, not an objection to it (see Conditions below).

### Conditions attached to this decision

This decision is **Proposed**, not Accepted, and carries three conditions:

1. **Principle 19 test must be completed before procurement.** Digital & IT to confirm in writing whether existing licensed platforms — including the Microsoft agreement — already provide adequate integration or event-brokering capability. If they do, Option B is delivered using that capability rather than a new purchase. This is the same duplication test the RIFF process applies to any request [SGP-C1].
2. **Availability treatment must be designed before the first integration cuts over.** The broker becomes a shared dependency; NFR-A-001 requires it not to become the estate's weakest point.
3. **Phasing must start with INT-001 and INT-005**, the SIS lifecycle and the placement grade flow — the two with the highest failure cost and, in INT-005's case, sensitive information handled manually (R-018, DR-004).

### Dissent recorded

No formal dissent at time of writing. **The cost objection is anticipated and legitimate**: BR-002 requires licence spend flat or reduced, and this option adds cost. The counter-argument is that support effort and the cost of the next rationalisation are also costs, currently unmeasured. This should be tested at RIFF rather than assumed in either direction.

| Sensitive placement data stops being re-keyed | Manual grade transfers | Routine → zero (R-018, DR-004) |
| Marginal integration cost falls | Effort for platform n+1 | Linear → constant |

### Negative — accepted trade-offs

| Trade-off | Mitigation |
|-----------|-----------|
| New licence or hosting cost against BR-002 | Principle 19 test first (Condition 1); offset against support effort and course-cloning single-person dependency |
| New shared runtime dependency | Availability design before first cutover (Condition 2); per-integration degradation rather than estate-wide failure |
| Operational skills the team lacks | Skills uplift in the implementation plan; managed service reduces but does not remove the need |
| Slower start than Option A | Phased adoption; INT-001 and INT-005 first rather than all nine |

- Integration standard document published and versioned (NFR-I-001)
- On-call and runbook coverage extended to the broker
- Schema change process established, since the canonical model becomes a runtime contract
