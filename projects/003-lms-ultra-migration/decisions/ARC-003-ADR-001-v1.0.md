## Context and Problem Statement

### Problem

The University of Funk must migrate from Blackboard Learn Original to Blackboard Ultra. This is simultaneously three things:

1. **A vendor-forced platform migration.** Anthology's end-of-support trajectory for Learn Original removes the option of staying indefinitely. The question is not whether to migrate, but how.
2. **The opportunity to implement the integration architecture from ADR-001 (Project 001).** Ultra's REST API surface is materially better than Learn Original's nightly flat-file. The integration re-engineering specified in `ARC-001-ADR-001-v1.0` — event-driven mediation through a canonical model — cannot be delivered against Learn Original's integration surface.
3. **A change that affects every academic, every student, and every unit site across all faculties.** This is not a backend re-engineering that can be invisible. Every teaching academic interacts with the LMS daily during teaching periods.

The decision is **how** to migrate — not whether. "Whether" is decided by the vendor's end-of-support.

### Why the decision is needed now

The migration is the critical path for three outcomes: the integration modernisation from Project 001 (which requires Ultra's APIs), the consistent accessible templates specified in G-4, and the event-driven PeopleSoft lifecycle in G-1. Until the migration approach is decided, the integration team cannot sequence their re-engineering work, Faculty Deans cannot plan academic change management, and the project has no basis for a business case timeline.

Conflict C-1 (migration pace vs academic disruption) and Conflict C-2 (integration scope vs team capacity) from `ARC-003-STKE-v1.0` both turn on this decision. Deferring it does not reduce the conflict — it compresses the available migration windows.

## Considered Options

1. **Option A** — Big-bang migration
2. **Option B** — Phased faculty-by-faculty migration
3. **Option C** — Parallel-run migration
4. **Option D** — Do Nothing (baseline)

### Option A: Big-bang migration

**Description**: All faculties migrate simultaneously in a single inter-semester window. Integration re-engineering happens beforehand; cutover is one event. Learn Original is decommissioned on a single date.

**Implementation approach**: Complete all integration re-engineering (INT-001 to INT-007) before the migration window. Migrate all unit sites, templates, and content in one inter-semester break. Train all academics in the same period. Single cutover date; Learn Original enters read-only archive mode.

**Wardley evolution stage**: Custom-built (0.30) — the migration itself is a one-off event with no opportunity to iterate.

**Good**:

- Shortest dual-running period — integration team maintains both platforms for weeks, not semesters
- Cleanest break — no ambiguity about which platform is current; Principle 3 (consistent experience) restored immediately
- Single training programme, single communications campaign, single support surge
- Lowest total licensing overlap cost — dual Blackboard licensing measured in weeks

**Bad**:

- **Highest single-event risk.** If anything fails — content migration, integration cutover, template configuration, academic readiness — everything fails. There is no contained blast radius
- No learning from early cohorts — the first faculty to migrate is also the last; mistakes are discovered at scale
- Rollback is all-or-nothing: reverting the entire university to Learn Original after a failed big-bang is operationally catastrophic
- **Integration re-engineering must be complete before migration begins**, which means the integration team is fully loaded before any faculty validation has occurred
- Massive change management in one window — every academic, every faculty, simultaneously. SD-5 (Clavinet: academic community carries the change) is incompatible with a forced simultaneous migration
- Inter-semester windows are 3-4 weeks. Migrating the entire estate plus validating all integrations in that window is aspirational, not realistic

**Cost analysis** *(indicative — AUD)*:

| | Estimate |
|---|---|
| CAPEX | Highest upfront — all integration re-engineering, all content migration, all training compressed into one phase |
| OPEX | Lowest ongoing — dual-running period measured in weeks |
| 3-year TCO | Lowest if it works. Highest if it doesn't — recovery from a failed big-bang dwarfs the phased alternative |

---

### Option B: Phased faculty-by-faculty migration

**Description**: Faculties migrate in cohorts across 2-3 inter-semester windows, each preceded by a pilot validation phase with willing academics. Integration re-engineering is sequenced: PeopleSoft lifecycle first (backend, invisible to academics), then faculty migrations with progressively proven integrations.

**Implementation approach**: Phase 0 delivers PeopleSoft → Ultra event-driven integration (INT-001), accessible templates (FR-005 to FR-008), and the pilot programme (FR-012). Phase 1 migrates a willing pilot faculty with tested integrations. Phase 2-3 migrates remaining faculties in cohorts, sequenced by discipline complexity and Dean readiness. Each phase has a tested rollback to Learn Original.

**Wardley evolution stage**: Custom-built (0.40) — structured programme with repeatable migration patterns, but each faculty has discipline-specific content requiring verification.

**Good**:

- **Risk contained per cohort** — a failed faculty migration is recoverable without affecting unmigrated faculties. The blast radius is bounded
- Learning from each phase — pilot validates content migration, templates, LTI integrations, and academic training before scale
- Integration sequencing — PeopleSoft re-engineering (INT-001) can be proven in Phase 0 before any faculty depends on it
- Academic calendar alignment — each migration occurs in an inter-semester window; no single window must carry the entire estate
- Per-faculty verification of discipline-specific tools (Music performance capture, Health Sciences clinical placement, Fine Arts portfolio) before their faculties migrate (Principle 4)
- Dean sign-off per faculty — Key and Anand can verify readiness for their discipline-heavy faculties before committing
- Rollback tested and verified before each phase, not assumed

**Bad**:

- **Longest dual-running period** — Learn Original and Ultra run simultaneously across 2-3 semesters. Integration team maintains both platforms throughout (R-005, G-5)
- Content linking between migrated and unmigrated faculties may break — cross-listed units, shared resources, and inter-faculty programmes are affected
- Dual licensing cost — Blackboard Original and Ultra licences overlap for 12-18 months
- Student experience is inconsistent during the transition — some units on Original, others on Ultra (Principle 3 violated for longer)
- More complex communications — "which platform is my unit on?" is a real student question during transition
- Integration team maintains dual integration surfaces for the duration, increasing support load

**Cost analysis** *(indicative — AUD)*:

| | Estimate |
|---|---|
| CAPEX | Spread across phases — lower peak spend but longer duration |
| OPEX | Highest ongoing — dual licensing for 12-18 months; dual integration support |
| 3-year TCO | Moderate. Higher than big-bang if big-bang succeeds; materially lower if big-bang fails |

### Option C: Parallel-run migration

**Description**: Both Learn Original and Ultra run simultaneously for an extended period. Academics migrate voluntarily. No hard cutover — gradual adoption until Learn Original usage drops below a threshold, then decommission.

**Implementation approach**: Ultra made available alongside Learn Original. Academics offered training, templates, and support to migrate their units at their own pace. Integration re-engineering delivers dual-platform support. Learn Original decommissioned only when usage drops below a defined threshold (e.g. < 15% of active unit sites).

**Wardley evolution stage**: Custom-built (0.25) — the migration is not a managed programme; it is an adoption curve with no guaranteed endpoint.

**Good**:

- Lowest coercion — academics migrate at their own pace; strongest alignment with SD-5 (academic community carries the change)
- Lowest single-event risk — no big cutover, no migration window pressure
- Academics who are enthusiastic early adopters validate the platform for those who follow
- No inter-semester window dependency — migration happens continuously

**Bad**:

- **Indefinite dual-running cost** — double licensing, double support, double integration engineering. BR-002 (integration re-engineering through canonical model) requires both platforms be integrated, doubling the work
- **No clear end date.** Adoption may stall at 60-70% — the enthusiasts migrate early, the reluctant never do. The tail is long and expensive
- Inconsistent student experience for the entire parallel period — the same student may have units on both platforms. Principle 3 (consistent experience) violated not temporarily but structurally
- Integrations must work on both platforms for an undefined duration — the integration team from G-5 is committed to dual maintenance with no scheduled release
- **Does not satisfy BR-001** (zero assessment-period disruption) because academics migrating mid-semester may disrupt their own students during assessment
- Voluntary adoption without deadline produces the worst-case scenario for student-facing consistency (SD-13, Field: "students not the experiment")
- Violates Principle 19 in reverse — the university pays for Ultra capability that a significant minority may never adopt

**Cost analysis** *(indicative — AUD)*:

| | Estimate |
|---|---|
| CAPEX | Lowest upfront — no concentrated migration programme |
| OPEX | Highest ongoing and for longest duration — dual licensing, dual integration, dual support until decommission |
| 3-year TCO | Highest. Duration is unbounded; cost compounds |

---

### Option D: Do Nothing (baseline)

**Description**: Continue on Learn Original. Do not migrate to Ultra.

**Good**:

- No cost, no disruption, no risk introduced
- Staff know the current platform's failure modes and workarounds

**Bad**:

- Vendor end-of-support removes this option on Anthology's timeline, not the university's — this is a deferral, not a decision
- Cannot implement the integration architecture from `ARC-001-ADR-001-v1.0` — Ultra's REST APIs are required; Learn Original's integration surface is the nightly flat-file
- All Project 001 integration outcomes blocked — event-driven PeopleSoft lifecycle (G-1) cannot be delivered against Learn Original
- Accessible templates (G-4, P14) constrained by Learn Original's template capabilities
- Principle 19 violated — Ultra is licensed and paid for; Learn Original is the capability being retired

**Retained as a genuine baseline**, not a strawman: the RIFF pause provision permits deferring a migration. But the vendor end-of-support trajectory makes this a decision to migrate later under worse conditions — less time, fewer windows, higher pressure. Every semester of deferral compresses the remaining timeline (R-010).

## Decision Outcome

**Chosen option: Option B — Phased faculty-by-faculty migration**, with integration re-engineering sequenced ahead of faculty migrations and a mandatory pilot programme before any faculty-level cutover.

### Y-Statement

> In the context of **migrating the entire university from Blackboard Learn Original to Ultra across all faculties, all students, and all unit sites**,
> facing **a vendor-forced migration that is also the vehicle for delivering the integration architecture from Project 001, and a change management challenge that affects every teaching academic**,
> we decided for **a phased faculty-by-faculty migration across 2-3 inter-semester windows with a pilot validation phase and sequenced integration re-engineering**,
> and against **big-bang migration, parallel-run voluntary adoption, and deferral**,
> to achieve **bounded risk per migration cohort, validated integrations before faculties depend on them, per-faculty verification of discipline-specific tools, and academic calendar alignment**,
> accepting **a longer dual-running period with dual licensing and dual integration support, inconsistent student experience during the transition, and a more complex communications and support model**.

### Justification

**Why not Option A** (big-bang), despite the shortest dual-running period: the blast radius is unbounded. A failed big-bang migration — content that doesn't render, an integration that drops enrolments, a template that fails accessibility — affects every faculty simultaneously with no rollback that doesn't mean reverting the entire university. The integration team must complete all re-engineering before any faculty validation, which means the most complex work is done with the least evidence. The inter-semester window is 3-4 weeks; the assertion that the entire estate can be migrated and validated in that window is aspirational. SD-6 (Castle: "do not break my units") is the voice of every academic whose content is at risk in a big-bang.

**Why not Option C** (parallel-run), despite the lowest coercion: it has no end date. Voluntary adoption produces an adoption curve that stalls when the enthusiasts are done, leaving a long tail of holdouts. The university pays dual licensing for an undefined period, the integration team maintains dual surfaces indefinitely, and students experience an inconsistent platform — some units on Original, some on Ultra — not for a bounded transition but as a structural condition. SD-13 (Field: "students not the experiment") is violated not temporarily but permanently. Principle 3 (consistent experience) becomes unachievable.

**Why not Option D** (do nothing): the vendor's end-of-support trajectory removes this option. Deferral does not avoid the migration; it compresses the available windows and increases R-010 (timeline too compressed). Every semester of inaction narrows the options.

**Why Option B despite the dual-running cost**: it is the only option that bounds the blast radius per phase, allows learning from early cohorts, and sequences integration re-engineering so that PeopleSoft → Ultra (INT-001) is proven before any faculty depends on it. The dual-running cost is real and the longest of the active options — but it is bounded (12-18 months), unlike Option C where it is open-ended. The academic calendar alignment means each migration occurs in an inter-semester window when disruption is minimised. Faculty Deans sign off before their faculties migrate, which is both a governance control and a change management mechanism.

### Conditions attached to this decision

This decision is **Proposed**, not Accepted, and carries five conditions:

1. **Pilot programme must validate with willing academics before any faculty-level migration.** FR-012 is a precondition, not a nice-to-have. The pilot must include content migration, template deployment, LTI integration verification, and academic training. If the pilot surfaces material issues, subsequent phases are delayed until they are resolved.
2. **PeopleSoft → Ultra integration (INT-001) must be event-driven and stable before the first faculty migrates.** The integration re-engineering from `ARC-001-ADR-001-v1.0` is sequenced into Phase 0. If INT-001 is not stable, no faculty migration proceeds — academics cannot migrate to a platform where enrolment data arrives overnight by flat-file.
3. **No faculty migrates during assessment or examination periods.** BR-001 and G-3 are absolute constraints. Migration activities — including content migration, template deployment, and integration cutover — are prohibited during assessment periods. This is non-negotiable.
4. **Faculty Deans must sign off before their discipline-heavy faculties migrate.** Key (Music, Fine Arts) and Anand (Health Sciences, Engineering) must confirm that discipline-specific tools — performance capture, clinical placement systems, portfolio platforms — work on Ultra before their faculties are scheduled.
5. **Rollback to Learn Original must be tested and verified before each phase.** NFR-A-002 requires migration rollback capability. Each phase must have a tested, documented rollback procedure. Rollback is tested in a staging environment before each phase begins, not assumed.

### Dissent recorded

**Anticipated dissent from Ostinato (CFO)**: the dual-running period is the longest and most expensive of the active options. Dual Blackboard licensing for 12-18 months, dual integration support, and a longer project timeline all increase visible cost. The counter-argument is that the cost of a failed big-bang — emergency remediation, academic disruption during teaching, reputational damage, and compressed re-migration — is larger but less visible in a business case. This should be tested at Education Committee with realistic cost comparisons, not assumed in either direction.

**Anticipated dissent from Castle (academic staff representative)**: phased migration means change fatigue. Academics who are not in the first cohort live with the knowledge that migration is coming, and the transition period is longer. Castle's SD-6 ("do not break my units") is better served by phased migration than big-bang — but the anxiety of waiting is real. Mitigation: clear published schedule so academics know when their faculty migrates and have time to prepare.

- **Rollback test**: Staged rollback rehearsal before each phase, with documented results

| Student platform confusion reports | Below threshold per phase | Student services |
| Rollback invocations | Zero (but capability verified) | Migration operations |
| Assessment-period migration activities | Zero (BR-001) | Migration schedule audit |

### Compliance verification

- **Privacy Act 1988** — content migration must not create unnecessary copies of personal information; migration staging environments cleared after each phase
- **ASD Essential Eight** — Ultra configuration must meet ML2 target before migration; service credentials for integrations managed centrally, not per-faculty
- **WCAG 2.2 AA** — Ultra templates verified against accessibility standard (P14) before any faculty migrates; accessibility audit per template
- **RIFF governance** — phased migration approach reviewed under RIFF process; dual licensing cost justified against migration risk reduction

> **Framework applicability note**: GDS Service Standard, Technology Code of Practice and NCSC Cyber Essentials are UK Government frameworks used as methodology references in the ArcKit escalation framework. They have no compliance standing for an Australian university. The applicable obligations are the Privacy Act 1988, the ASD Essential Eight, WCAG 2.2 AA, and the university's own RIFF process.
