## 1. Decision Title

**All 12 stores consolidate onto a single cloud POS platform, integrated
exclusively as a spoke of the inventory/order hub, with customer identity
tokens from the CRM. The POS never integrates directly to MYOB/ERP or to the
e-commerce platform.**

**ADR Status**: Proposed (integration pattern accepted; platform pending
evaluation)

- **Deciders (A):** Betty Rubble (platform), Wilma Flintstone (pattern),

- **Consulted (C):** Store managers (3 cohorts), workshop leads, Jane Jetson

- **Informed (I):** All retail staff; payments acquirer

## 3. Context

Three POS estates from acquisitions; June 2027 contract deadline; new hub
(Project 001) becoming the inventory master; CRM (Project 002) becoming the
customer master. The temptation in POS projects is direct integrations —
POS→accounting for speed, POS→web for click-and-collect — creating exactly
the point-to-point sprawl the portfolio pattern (ARC-000-PORT §2, PR-2)
prohibits.

## 4. Decision

1. **One platform** for all 12 stores (options per ARC-004-RSCH shortlist).
2. **Hub-only data plane:** stock queries, sales/return events, transfers,
   and click-and-collect states flow POS↔hub. Financial postings reach
   MYOB/ERP only via the hub (INT-001, NFR-I-001).
3. **CRM-tokenised customers:** POS holds loyalty tokens, not customer
   profiles (DAT-004); consented notifications route via CRM.
4. **Pilot gate:** one store from each legacy cohort passes a 2-week
   zero-variance pilot (incl. forced-offline test) before chain rollout.

## 5. Options Considered

| Option | Summary | Verdict |
|---|---|---|
| A — Keep three estates, integrate each to the hub | Lowest retraining | Rejected: triple integration + triple training forever; fails G-1 |
| B — Standardise on largest incumbent by default | Fast decision | Rejected as default; incumbent competes on merit in evaluation |
| **C — Single platform, hub-first, CRM-tokenised (chosen)** | Pattern above | **Accepted** |
| D — Single platform with direct POS→MYOB posting | Familiar to vendors | Rejected: recreates the pre-001 architecture; breaks ERP supersession invariant (ARC-003-ADR-001 §4.4) |

## 6. Rationale

1. **The ERP cutover invariant depends on it.** If POS posts directly to
   MYOB, Project 003's "re-point one integration" promise (G-5) is broken.
2. **One customer truth.** Tokenisation keeps Privacy Act surface in one
   audited system (Project 002 PIA), not twelve store databases.
3. **Contract clock.** A single-platform decision path is the only one that
   completes rollout before June 2027 with a peak-trade freeze (BR-009).

## 7. Consequences

- **Positive:** portfolio integration count stays flat; ERP cutover remains
  contained; chain-wide stock and loyalty become real.
- **Negative / accepted:** the winning platform must expose hub-grade event
  APIs — this disqualifies otherwise attractive products; two store cohorts
  retrain fully; payments migration coordinated with the acquirer.
- **Conditions:** joint checkpoint with Project 005 before platform sign-off
  (ARC-004-RSCH R-2); SAQ scope assessment before pilot (G-6).
